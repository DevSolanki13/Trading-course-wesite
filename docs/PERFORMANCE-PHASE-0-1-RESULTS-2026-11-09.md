## Baseline evidence and limits

[Measurement harness](../backend/scripts/measure-optimization.mjs) starts the existing isolated production fixture preview on port 3112; it does not use the user's port-3000 session or shared services. It captured 16 screenshots, a normal-motion video, a Playwright motion trace and three Lighthouse reports under [baseline output](../artifacts/optimization/phase-0-before-content-ready/summary.json).

Baseline build: `hZ1RiBmwo2CjqvGK2O9fR`. Verified implementation build: `aYvgngVpnOpVI18PspcmE`.

**Do not use these Lighthouse runs as a comparable baseline or a speed-gain claim.** All three warned that loading exceeded the time limit and results might be incomplete. The old harness also reused a browser profile: the first run included the once-per-browser video, while later runs did not. Observed transferred bytes changed from approximately 16.31 MB to 1.12 MB for that reason, not because this batch improved delivery. No before/after median or improvement percentage is claimed.

The harness now creates a fresh Chrome profile for each future Lighthouse sample. That correction still needs three complete, scenario-labelled samples and a matching after run. Public first-time/returning visits, private-route baselines, cache hit/miss conditions, request counts and route-specific budgets remain open. Screenshots are not frame-rate measurements, and fixture latency is not hosted database/provider latency.
