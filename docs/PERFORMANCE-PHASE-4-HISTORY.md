## Contract and bounds

- [Dedicated migration](../backend/database/migrations/202611090043_purchase_history_page.sql) adds service-role-only `purchase_history_page`, preserving `purchase_read` and every UPI wrapper. A verified admitted user supplies the owner ID server-side. Public, anonymous and authenticated SQL execution is revoked; fixed empty search path and explicit owner predicates protect privileged reads.
- [Repository](../backend/purchase/repository.ts) exposes `purchaseOrdersPage(userId, options)`. GET `/api/purchase/orders?limit=20` selects this contract; limit is 1–50. `status` accepts all/pending/paid/failed/cancelled/refunded; `provider` accepts all/mock/razorpay/upi/cashfree/demo. Both filters precede LIMIT. Cursors are JSON `{createdAt,id}` and validated at the handler and SQL boundary. Timestamp text retains PostgreSQL microseconds; the client never round-trips it through JavaScript Date.
- One owner-scoped orders relation contains every provider. The page selects at most `limit+1` detail rows, then enriches at most `limit` rows with immutable financial/course snapshots and enrollment expiry. It does not load complete provider arrays or slice full history in JavaScript. Ordering and cursor comparison both use descending `(created_at,id)`.
- `totalCount`, `totalAmount` (all order amounts, including pending/refunded), `paidAmount` (currently paid only), and `pendingCount` always cover all the owner's orders. `filteredCount` covers the selected filters before pagination. Exact aggregates necessarily inspect owner-scoped scalar data across history; full order JSON and detail joins remain bounded. This is not a claim of constant-time exact totals.
- Every page includes at most four pending references plus an independent pending cursor, ignoring visible-page filters. `pending=1&pendingCursor=...` skips the history-detail branch entirely and returns the next bounded pending batch plus exact summary scalars. More than four pending orders use this query each poll; periodic history refresh does not rewind that cursor. At the end it wraps. Manual refresh, focus and visibility resume reset discovery; queued focus refresh also resets after an in-flight request completes.
- Cashfree/demo status checks remain bounded to four per cycle, every five seconds, with at most 40 automatic cycles. Simple pending histories still perform seven page reads and 40 status checks over the existing bounded polling window. Page reads otherwise occur every 30 seconds, on focus/manual refresh, or after settlement. Off-page unsupported pending providers (including UPI) retain five-second saved-history refresh behavior. The aggregate unsupported count keeps discovery alive even when that provider is outside the current page and pending batch. Hidden/inactive/unmounted views stop work; requests are abortable and do not overlap.
- Both active dashboard SSR entry points load one bounded page. Counts/badges use global totals, and the UI provides Previous/Next and filters. Receipts keep provider-specific routes. No-query orders and the old dashboard API preserve their full-history compatibility responses; neither is the active billing UI's history source. Checkout's existing UPI duplicate-order discovery continues using the compatibility helper.

## Local evidence

[Isolated database test](../tests/phase4-history.test.ts) applies the complete migration chain to a fresh in-memory PGlite database, without using shared local or hosted data. It verifies all five providers, 120 historical orders, equal timestamps with microseconds, 17-row pages through exhaustion, exact counts/amounts, filtered traversal, immutable course titles, receipt routes, 30 pending references across batches despite unrelated filters, older settlement without total/count loss, service-role execution and denied anonymous/authenticated execution. It also reads the unchanged UPI single-order wrapper and checks the original gateway URI/gateway fields.

Both new indexes have isolated `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)` comparisons. The fixture has 4,000 paid rows with tied timestamps and five pending orders for a separate owner:

| Read                         | Without added index                                                            | With added index                                                   |
| ---------------------------- | ------------------------------------------------------------------------------ | ------------------------------------------------------------------ |
| 21-row history detail keyset | Existing `(user_id,created_at)` index read 4,001 rows and incrementally sorted | `(user_id,created_at DESC,id DESC)` returned 21 directly           |
| Five pending references      | History index removed 4,000 paid rows by filter; 4,009 buffer hits             | Partial pending cursor index returned five rows; three buffer hits |

Observed focused pending execution was 2.081 ms before and 0.243 ms after. These are disposable fixture observations, not hosted latency promises. Tests print the full plans, allowing reruns; production data distribution, index build locks/cost, target PostgreSQL planner and PostgREST still require rollout acceptance. No speculative provider/status-filter indexes were added.

[UI tests](../tests/phase4-history-ui.test.tsx) verify bidirectional tied-date cursors, filters reset to page one, provider receipt links, global totals, an older-page saved receipt after settlement, 36 pending checks across the 30-second page refresh, focus/manual cursor reset, and off-page UPI polling/stop after settlement. [API tests](../tests/phase4-history-api.test.tsx) verify verified-owner scope, bounded arguments, private/no-store headers, invalid inputs, admission failure and no-query compatibility. [Existing billing tests](../tests/billing-sync.test.tsx) preserve Phase 3 request counts with the paginated URL and verify the repository uses one bounded RPC rather than full provider reads.

Executed verification: full UI suite passed 262 tests across 40 files before the final added repository assertion; full backend suite passed 79 tests with zero failures. After the final polling/cursor change, the affected six-file UI/API/dashboard/billing set passed 59 tests, and the isolated migrated DB fixture passed again. TypeScript, scoped ESLint, changed-file Prettier checks and whitespace checks passed. SQL uses the repository's existing plain-SQL format; Prettier has no SQL parser installed.
