## 3. Video protection: what can actually be enforced

- **In place:** premium files are absent from `public/`; the app stores provider IDs privately and requests VdoCipher DRM OTPs server-side only after entitlement and device checks. Every response is private/no-store. The OTP is short lived (five minutes), site-bound by a URL whitelist, and the provider receives a moving viewer-email watermark. No offline license or MP4 download route is issued. The UI requests Picture-in-Picture disable and ends playback when heartbeat validation fails.
- **In the browser:** the player necessarily receives an OTP and encrypted media bytes. Developer tools can reveal those network requests. DRM is what prevents those bytes from becoming a playable MP4 without a valid license; hiding DevTools or blocking right-click cannot provide that protection.
- **Screen recording:** a web page cannot guarantee that another device, capture card or camera cannot record its screen. Provider DRM/output protection can block some software capture paths; the visible watermark discourages redistribution and helps investigate leaks. Do not promise complete screen-record blocking to buyers.
- **Verification required:** test real paid and free-preview playback in normal Chrome/Edge with protected content enabled, Android Chrome and iPhone Safari. Confirm DRM, watermark, browser quality/speed controls, the new URL whitelist, revoked access, and screen-capture behavior on each target device. The existing headless test browser lacked Widevine, so a working OTP is not a passed DRM test. Review the VdoCipher dashboard's domain and offline settings before publication. Use a real publisher account and content only with authorisation.

References: [VdoCipher OTP API](https://www.vdocipher.com/docs/server/playbackauth/otp/), [minimum OTP TTL guidance](https://www.vdocipher.com/docs/server/playbackauth/ttl/), [URL whitelist](https://www.vdocipher.com/docs/server/playbackauth/whitelist/), [capture limitations](https://www.vdocipher.com/blog/screen-capture-block-video/).

## 4. Where to store about 8 GB of source video

**Recommendation: keep premium course videos in VdoCipher**, which this app already integrates. Upload two 4 GB source courses there as private lessons, keep the original masters in a separate private backup, and use the provider for transcoding, adaptive delivery, CDN and DRM. The 8 GB figure is source size; provider storage after encoding and billed delivery traffic depend on runtime, resolutions, and learners, so request a quote using **total video minutes, expected viewing hours per month, India delivery, desired resolutions, and DRM/watermark features**. Confirm file-size/upload limits and backup/export policy before upload. Do not put course files in this repository, Vercel functions, a public Supabase bucket, or a public Cloudinary URL.

## 5. Security posture and remaining exposure

Changes in this work: request-specific nonce CSP, iframe restrictions, HTTPS HSTS on configured HTTPS deployments, no cache for private pages, strict input validation, same-origin and admitted-session checks for simulated payment, strong demo secret, five-minute webhook timestamp window, server-authoritative price/tax/course snapshot, and atomic/idempotent order settlement. Payment SQL grants execution only to the service role. A local PostgreSQL-compatible test covers role denial, amount mismatch, replay, terminal-state safety, and rollback of a failed enrollment write. The learner library continues to work when refund status cannot load. The dependency audit reported **zero known production advisories** at the time of this run.

Existing controls include parameterized database access, RLS on sensitive tables, signup role fixed to student, server-only service key, verified sessions and two-device admission, staff-only MFA, validated course IDs and payload sizes, rate limiting backed by the database, checked Cashfree signatures, and disabled real checkout. These reduce common SQL injection, key disclosure and role escalation paths; they do not make the website invulnerable.

Before a real launch: apply and verify the new migration in **staging first**; test role/CSRF/payment paths against that staging deployment; enable platform WAF/bot and edge rate limits; monitor auth and payment failures; rotate and scope credentials; verify backup restore and alerting; finish Cashfree signature, amount, status and settlement reconciliation; commission an independent security review after real content and payment integration. Keep demo payment variables unset on production and remove any test course. Do not issue a launch approval based only on the local checks.
